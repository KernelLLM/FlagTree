# dequantize_and_gather_k_cache

## 1. 测试方法

- 在海光bw1000上进行测试。共三轮独立进程，每轮每版 20 次预热、50 个有效 GPU-event 样本

## 2. 改变了哪些 op 的 layout

改变量化块与 RoPE 向量的 `gl.arange` 分布，并用于 FP8/scale/BF16 的 `gl.load → 解码/乘 scale → gl.store`：

- 基线：`BlockedLayout([1], [64], [4], [0])`，`num_warps=4`。
- 优化：`BlockedLayout([1], [64], [1], [0])`，`num_warps=1`。

两版均 `num_stages=2`、grid=`(B,128)`。仅布局及对应 CTA wave 数不同，数据格式、索引、mask、循环和算法不变。

### 配置 B/S/G；C；NoPE/RoPE；offset 的含义

- **B**：batch size，即请求/序列数。
- **S**：本表每个请求的有效序列长度，单位为 token，对应 `seq_lens`。
- **G**：每个请求从序列末尾取出的 token 数，读取区间为 `[S-G, S)`；`full` 表示不传 `gather_lens`，取整个序列（G=S）。
- **C**：每个分页 cache 块能存放的 token 数，即 `block_size`，不是总块数或字节数。
- **NoPE/RoPE**：每个 token 的 FP8 解量化部分维数 / 直接拷贝的 BF16 RoPE 部分维数；输出最后一维为两者之和。
- **offset**：输出张量中的起始 token 位置，写入 `out[b, offset:offset+G, :]`，**不是 cache 的读取偏移**。

例如 `2/192/65；64；96/32；2`：2 个请求，各有 192 个 token，分别取最后 65 个；每个 cache 块容纳 64 个 token，输出每 token 为 96+32=128 维，写入 `out[:, 2:67, :]`，前两个 token 位置不写入。
